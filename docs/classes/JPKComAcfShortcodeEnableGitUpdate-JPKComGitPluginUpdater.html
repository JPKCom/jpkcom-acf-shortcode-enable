Class JPKComGitPluginUpdater

Handles plugin updates from GitHub-hosted JSON manifests.

Why a family: WordPress only runs the code of ACTIVE plugins, so a copy of this class inside an inactive plugin never hooks anything and that plugin would never be offered an update. Every JPKCom plugin therefore registers its copy in a shared registry, and the copy with the highest UPDATER_VERSION (ties: the first registered) does the work for every installed JPKCom plugin. All other 1.5+ copies stay passive. Copies older than 1.5 do not know the registry and keep serving their own plugin; the leader leaves plugins whose old copy is loaded alone, so the two never disagree about a manifest or a package.

members()

class-plugin-updater.php : 375

The JPKCom plugins this leader serves, keyed by plugin file.

private members() : array<string, array{slug: string, folder: string, file: string, version: string, manifest: string, frozen: bool}>

Members are (a) every loaded 1.5+ copy from the registry and (b) every discovered JPKCom plugin whose code is NOT loaded in this request. A plugin that is loaded but not registered runs an older updater copy, which serves it against its own cache; the leader stays out of its way.

A member is "frozen" (only ever listed as up to date, never offered a package) when it is a version-control checkout, which an update would wipe, or when its folder is not named after its slug (e.g. jpkcom-foo-main from a GitHub source download): the release ZIP unpacks into jpkcom-foo/, so an update would delete the renamed folder and leave the active plugin missing.

The cache is tied to the registry, because copies register one by one during init and a transient read can happen in between.

Return values
array<string, array{slug: string, folder: string, file: string, version: string, manifest: string, frozen: bool}>
